# Sign-in, two-factor authentication and passkeys: UX research (2026-10-18)

Ledger `auth-ux-2026-10-18`. The owner asked on 2026-10-18 for the login pages, with motion and input-box design, to cover:

- two-factor authentication (2FA);
- adding passkeys;
- the login providers;
- for accounts that administrators added by e-mail (local accounts, not identity-provider accounts): resetting a user's 2FA, or sending a password-reset link.

This note collects the evidence. The design is in [`docs/design/v3/auth.md`](../design/v3/auth.md). The parallel backend lane AU-B writes `docs/research/2026-10-18-auth-backend.md`. That file did not exist when this note was written; §8 lists the API shape the screens expect, so AU-B can confirm or correct it.

Sources were checked on 2026-10-17/18 (UTC). The "Status" column says how directly each one was verified.

| S1 | NIST SP 800-63B-4 (final, July 2025), https://pages.nist.gov/800-63-4/sp800-63b.html | **Passwords (§3.1.1.2):** at least 15 characters for single-factor use, 8 when used inside MFA. No composition rules. Check against a blocklist and say why a password was refused. Allow paste and password managers. Offer a "show password" option. No periodic forced changes. No hints or security questions. **Rate limiting (§3.2.2):** at most 100 consecutive failures per authenticator. **OTP:** each code accepted once; time-based codes change at least every 2 minutes. **Look-up secrets:** at least 6 digits, single use. **Binding (§4.1):** several authenticators per account must be allowed; binding a new one needs authentication and a notification on an independent channel. **Recovery (§4.2):** saved recovery codes have at least 64 bits of randomness, are stored hashed and are single use; issuing replacements triggers a notice; "account recovery SHALL cause a notification". **Notification (§4.6):** binding and recovery events require a notice. **Sessions (§2.2.3, §5.2):** AAL2 overall timeout ≤ 24 h and inactivity ≤ 1 h. ## 5. Findings that shape the design

1. **No 2FA for identity-provider accounts.** People who sign in with Entra, Google, OIDC or SAML are protected by their institution. SmartSched must not add a second, different 2FA on top: that would mean double prompts and double help-desk work. Profil › Güvenlik says so in one line, and Admin › Kullanıcılar replaces the reset actions with "Bu hesap {sağlayıcı} ile giriş yapıyor".
2. **The 2FA methods are an authenticator app (TOTP), passkeys and recovery codes. No SMS and no e-mail codes.**
   - SMS costs money, is restricted by NIST and is exposed to SIM swap.
   - E-mail is already the password-reset channel, so an e-mail code would not be a second factor.
3. **A passkey is a full sign-in.** It counts as multi-factor: possession plus user verification. It also works as the second step after a password, through "Başka bir yöntem".
4. **The code input:** one real input drawn as 6 slots (C1). This combines the phone ergonomics of M10 with the accessibility and autofill of a single field (S9). Recovery codes use a plain single text field.
5. **Do not prompt for passkeys during sign-in** (S8). Use conditional create silently after a password sign-in (S4), and a calm card in Profil › Güvenlik. Never use a full-page interstitial.
6. **Step-up before any change to factors** (S2, S3): own password, passkey or current code. The step-up is valid for 10 minutes.
7. **Notify on every factor change, recovery-code use and admin reset** (S1 §4.2, §4.6; S2). This uses the themed e-mail system. See auth.md §8 for the missing kinds.
8. **Admin 2FA reset is a recovery path,** so it is audited, needs a reason, notifies the user, and offers to sign out the user's sessions (S2: "invalidate the replaced authenticator and revoke affected sessions"). Unlike Entra, the admin sees whether passkeys stay, with a "hesap ele geçirilmiş olabilir" reason that removes them too.
9. **"Bu cihazı 30 gün hatırla" conflicts with the letter of NIST §5.2,** which does not allow a remember-browser cookie in place of authentication. Common practice (Google, Employment Hero, GitHub) keeps it, and the owner asked for it. Our design limits it:
   - the password is always asked;
   - only the second step is skipped;
   - a change of password, a 2FA reset or "Diğer oturumları kapat" revokes the device;
   - the admin can switch it off by policy (auth.md §5).
   - Owner question Q3.
10. **Password length.** NIST requires 15 characters without MFA and 8 with it. Today the minimum is 8. The recommended default is 12 for new passwords and 8 when the account has 2FA; owner question Q2.
11. **Motion.** Only free transitions.dev recipes, at most 300 ms each, plus the one Lottie hero, which plays once and stays under 5 s so WCAG 2.2.2 needs no pause control.

| Risk | Mitigation |
|---|---|
| A user loses the phone and the recovery codes | Admin reset (auth.md §4) after verifying identity in person or by phone, never by e-mail alone. The dialog asks the admin to tick "Kimliğini doğruladım". |
| A shared lab or office PC with "remember this device" | Checkbox off by default, with the hint "Yalnızca kendi cihazınızda". The policy can disable it. Sessions list with "Oturumu kapat". |
| An attacker who holds the password adds a passkey | Step-up needs a second factor when 2FA is on. A `passkey_added` e-mail is sent. The admin reset reason "Hesap ele geçirilmiş olabilir" removes passkeys and sessions. |
| Enumeration through the 2FA step | The 2FA step appears only after a correct password. Reset and forgot-password answers stay identical. |
| Locking out the last admin when 2FA is "Zorunlu" | The grace period applies to admins too. The policy screen warns if no admin has 2FA yet, and the break-glass rules (sign-in.md) stay unchanged. |
| An SSO account with a local password (binding) | Local actions apply only if `auth_methods` includes `local`. The row shows both methods. |

## 8. Expected API (for AU-B to confirm; names illustrative)

| Screen need | Expected call |
|---|---|
| Password sign-in that needs a second step | `POST /auth/login` → `200 { mfa_required: true, challenge: { token, methods: ["totp","passkey","recovery"], expires_in, remember_allowed, remember_days } }` (no session cookie yet) |
| Verify the second step | `POST /auth/mfa/challenge/verify { token, method, code \| assertion, remember_device }` → session + `/auth/me` |
| Passkey sign-in (autofill and button) | `POST /auth/passkeys/login/options` → `PublicKeyCredentialRequestOptions` (empty `allowCredentials`); `POST /auth/passkeys/login/verify` |
| Enrolment required by policy | `/auth/me` or the login response carries `mfa_enrolment: { required: bool, deadline: ISO \| null }` |
| TOTP enrolment | `POST /auth/mfa/totp/start` → `{ secret, otpauth_uri, issuer, account }`; `POST /auth/mfa/totp/confirm { code }` → `{ recovery_codes: [...] }` (shown once) |
| Recovery codes | `GET /auth/mfa/recovery-codes/status` → `{ remaining, total, created_at }`; `POST /auth/mfa/recovery-codes/regenerate` |
| Turn 2FA off | `DELETE /auth/mfa` (refused with 409 `mfa_required_by_policy`) |
| Passkeys | `GET /auth/passkeys` → `[{ id, name, provider_name, provider_icon, backed_up, created_at, last_used_at }]`; `POST /auth/passkeys/register/{options,verify}`; `PATCH /auth/passkeys/{id} { name }`; `DELETE /auth/passkeys/{id}` |
| Step-up | `POST /auth/reauth { password \| code \| assertion }` → `{ valid_until }`; protected calls return 401 `reauth_required` otherwise |
| Sessions and trusted devices | `GET /auth/sessions` → `[{ id, device, current, last_seen_at, created_at, method, trusted_until }]`; `DELETE /auth/sessions/{id}`; `POST /auth/sessions/revoke-others` |
| Sign-in history | `GET /auth/sign-ins?limit=20` → `[{ at, result: success\|failed\|mfa_failed\|locked, method, device, city? }]` |
| Admin: status and actions | user list rows carry `mfa: { enabled, methods, passkeys }`; `POST /admin/users/{id}/mfa/reset { reason_code, reason_text?, revoke_sessions, remove_passkeys, identity_checked }` (audited); `POST /admin/users/{id}/password-reset-link` (refused 409 `sso_account` with `{ provider_label }`) |
| Org policy | `GET/PUT /admin/auth-policy { mfa_mode: off\|optional\|required, mfa_roles: [...], grace_days, passkeys_enabled, remember_device_days }` |
