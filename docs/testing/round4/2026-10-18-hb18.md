## 4. Findings

### Blockers

**HB18-F01 · Every helper confirm card is born expired in Europe/Istanbul (R1 writes impossible) · blocker**
- Repro: sign in as `akademisyen.ayse` with the browser in Europe/Istanbul. Press ⌘J (phone: Daha › Yardımcıya sor),
  type "yarın 10:00 A 204" and click "Kısayollar · Salon ayır: A 204 · yarın · 10:00".
- Observed: the card shows "Bu öneri eskidi." and only "Yenile". After "Yenile" the new card is expired again. The
  same happens to "Bunu hatırla" (`remember_note`).
- Expected: "Rezerve et: A 204 · 19.10.2026 Pazartesi 10:10–10:50" for 10 minutes.
- Cause: `expires_at` is a naive UTC datetime serialized with no offset (`"2026-10-18T13:11:22.83"`,
  `backend/app/ai/helper/confirm.py:146-148` `_ts()` drops tzinfo; `schema.py:231`). The client reads it with
  `Date.parse()` (`frontend/src/components/helper/cards/confirm.tsx:22-23`), which treats an offset-less ISO string as
  local time. In UTC+3 every token is about 2 h 50 min old at birth.
- The same parse affects `undo_expires_at` (`cards/result.tsx:25`, "Geri al" disappears up to 3 h early) and
  `recent.tsx`.
- Fix:
  - Serialize aware UTC with a "Z" suffix: keep `tzinfo=UTC` in `_ts()`, or add a pydantic serializer on the
    helper schema datetimes.
  - In the client, parse with an explicit UTC rule: append "Z" when no offset is present, through a
    `parseServerTime()` helper used by confirm, result and recent.
  - Add a vitest with `TZ=Europe/Istanbul` and an e2e that clicks a confirm card at `timezoneId: Europe/Istanbul`.

**HB18-F02 · Sign-in form submits as GET before hydration and puts the password in the address · blocker (security)**
- Repro: with the host loaded, open http://127.0.0.1:19901/login. Type the username, then the password, and press
  "Giriş" as soon as the fields appear (before React hydrates; reproduced 3 times by the lane's script).
- Observed: the browser navigates to `/login?username=<user>&password=<password>`. The password is now in the browser
  history and in the web server, proxy and analytics logs.
- Expected: no credential ever in a URL.
- Cause: `frontend/src/components/auth/local-sign-in.tsx:165`: `<form onSubmit={onSubmit} noValidate>` has no
  `method`, so the native submit is a GET with the `name="username"` / `name="password"` fields (lines 189, 234).
- Fix:
  - `method="post"` with an `action` that cannot leak, e.g. `action="/api/v1/auth/form-login"`, which 303-redirects
    back, or `action="#"`.
  - Keep "Giriş" `disabled` until hydrated.
  - Server: reject and never log `GET /login` with a `password` parameter.
- Handling note: the lane's own scratch output that caught the URL was redacted at once. The persona password was
  visible in one tool result, so the orchestrator may want to rotate `PERSONA_PW`.

### Major

**HB18-F03 · Helper refusals lose their message: a taken slot shows "Yanıt alınamadı" · major**
- Repro: as `akademisyen.ayse` (UTC workaround), get the confirm card "yarın 14:30 A 204". Let another user book that
  slot, then click "Rezerve et".
- Observed: an amber "Yanıt alınamadı. Arama ve kısayollar çalışıyor." The primary "Rezerve et" stays and offers no
  alternatives ([shot](shots/hb18-ayse-taken-1440.webp)).
- Expected: "Bu saat dolu." / "Bu saat az önce doldu." with "Başka saat öner". The API answers 409 with `detail` =
  `{code: "conflict", message_tr: "Bu saat dolu.", alternatives: […]}`.
- Cause:
  - `lib/api/client.ts:79-88`: `ApiError` accepts only a string or array `detail`, so an object `detail` stores the
    whole body.
  - `lib/api/helper.ts:147-158` `helperRefusal()` then reads `code` and `message_tr` one level too high.
  - So `use-helper-runner.ts:258-271` never matches `already_done`, `expired`, `changed` or `rate_limited`, and falls
    back to `helper.error.provider`.
- Fix: in `helperRefusal`, unwrap `raw.detail` when it is an object, or widen `ApiError.detail` to accept an object.
  Render the `alternatives` as "Başka saat öner" rows. Add a test on a 409 body of that exact shape.
