# AUX-12 · Sign-in, 2FA and passkeys: persona run of auth.md §16 (round 4, lane aux12-vo09)

## 1. BLUF

- **Counts:** 0 blocker · 3 major · 8 minor.
- **Verdict:** the 2FA, recovery-code, passkey, admin-reset and policy flows all work end to end in Turkish at 1440 and 390, and they are easy to follow.
- **What blocks sign-off:**
  - a login submit before hydration sends the password in the URL (AUX12-F01);
  - at 390 the setup sheet is a narrow side panel that cuts off the sixth code slot (F02);
  - the sessions list cannot name any device (F03).
- **Stack:** gracious (web 19901, API 19900, single uvicorn worker), commit `93cfd24`, tr-TR, Europe/Istanbul. Chromium 1194 (Playwright), with a CDP virtual authenticator (ctap2, internal, resident key, UV).

## 2. Setup and method

- **Accounts.** I created all of them in the browser through `/admin/users › Yeni kullanıcı` as `admin@smartsched.local`, with PERSONA_PW. A copy of `t/setup-personas.mjs` did this.
  - `aux.admin` (Yönetici): the admin side.
  - `aux.plan1` / `aux.plan2` (Planlamacı): TOTP at 1440 / 390.
  - `aux.pk`, `aux.pk2`, `aux.pk3` (Öğretim elemanı): passkeys.
  - `aux.cc`: Conditional Create.
  - `aux.reset`: password reset link and code.
  - `aux.policy` (Planlamacı): check 9.
  - `aux.sess`, `aux.sess2`: AU-B sessions.
  - `aux.voice`: Part B.
  - I did not change any shared persona or `admin@smartsched.local`, apart from the shared global settings listed below.
- **Method.**
  - Every screen was driven by hand: typing, clicking, pasting, Escape. Each flow ran at 1440 mouse and at 390×844 touch (isMobile, hasTouch, tr-TR).
  - TOTP codes were computed in the script from the key shown in "QR kodunu tarayamıyor musunuz?" (RFC 6238). Keys, codes and passwords were never printed; screenshots mask the key, the QR, the recovery codes and the reset code.
  - The API was used only to verify results: `/admin/users/{id}/mfa`, `/audit`, `/booking-admin/outbox` (the mail outbox, see below), `/auth/sessions`, `/admin/auth/mfa-policy`.
- **E-mail.** No SMTP sink is configured (`GET /mail/status` → `not_configured`). Every security mail is queued UNSENT in `notification_outbox`, and an admin can read it with `GET /api/v1/booking-admin/outbox`. I used that as the sink: kind, subject and body checked.
- **Global settings changed and restored:**
  1. `public_url`: set to `http://localhost:19901` for about 3 min, three times, for the passkey runs, then restored to empty. WebAuthn refuses an IP address as RP ID, so those runs used `http://localhost:19901`.
  2. `auth.passkey_first_factor`: turned on in the UI three times, then back off in the UI.
  3. MFA policy: Zorunlu (Yönetici + Planlamacı, 14 gün) for about 90 s, then restored in the UI to `optional / ["ADMIN"] / 14` (verified by API).
  - Side effect of step 3: 8 `mfa_required` mails were queued (UNSENT) to people in scope, including shared personas. Admin and planner sign-ins during those 90 s would have seen the enrolment notice, with "Daha sonra".
- **Repo specs.** `e2e/au-signin-security.spec.ts` ran three times and `e2e/au-signin-hero.spec.ts` ran twice (`E2E_REAL=1`, `PW_PORT=19901`; the config reuses the running server). Results are in §3.2.

## 4. Findings

### AUX12-F01 · Sign-in submitted before hydration sends the password in the URL · major (security)

- **Repro:**
  1. `http://127.0.0.1:19901/login`.
  2. Type a username and a password, then press Enter before the JS bundle has hydrated (on a loaded host or a slow phone). To reproduce every time: JavaScript off, username `aux.nobody`, password `dummy-not-a-password`, Enter.
- **Observed:**
  - The browser does a native GET to `/login?username=aux.nobody&password=dummy-not-a-password`.
  - The password lands in the address bar, the browser history and any access log on the path.
  - It also happened in a real run here: the admin account's sign-in on a cold `localhost:19901` page showed `/login?username=aux.admin&password=…` in Playwright's navigation log.
- **Expected:** a pre-hydration submit never puts credentials in a URL.
- **Where:** `frontend/src/components/auth/local-sign-in.tsx:165`, a `<form onSubmit=…>` with no `method`, and fields named `username` / `password` at lines 189 and 234.
- **Fix:**
  - add `method="post"` (and `action="/login"`, or a no-op action, so a native submit is at worst a POST without a query);
  - keep "Giriş yap" `disabled` until hydrated (a `useEffect` flag);
  - optionally drop `name="password"`: password managers use `autocomplete`.
  - The same applies to `set-password-form.tsx:93` and `reauth-dialog.tsx:104` (no `method` either).

### AUX12-F03 · Sessions list: every session is "bilinmeyen tarayıcı, bilinmeyen cihaz" · major

- **Repro:**
  1. `aux.sess` signs in on a desktop (Chrome) and on a phone with a Safari iPhone UA.
  2. `/profile#security` › Oturumlar ve cihazlar.
  3. Or call `GET /api/v1/auth/sessions` from the phone.
- **Observed:**
  - All rows, the current one included, read "bilinmeyen tarayıcı, bilinmeyen cihaz" (API `device` is the same).
  - The person cannot tell which row is the phone, so "Oturumu kapat" is a guess. In my run I ended "the first other row", and it happened to be the phone.
  - The remembered-device row, recorded at login, correctly says "Chrome, Linux".
  - `network` is `127.0.0.0/24` for all rows, expected on this local stack.
  - See `shots/aub-sessions-phone-390.webp`, `shots/aux12-sessions-devices-1440.webp`.
- **Expected:** "{browser} · {os}", for example "Safari, iPhone" (e2e-queue AU-B item 1; auth.md §6.5).
- **Where:** `backend/app/services/sessions.py:142` takes the User-Agent of the token's first request. That is probably the Next server's own request (the proxy `app/api/v1/[...path]/route.ts:50` forwards `user-agent` for browser calls, but server-side fetches carry the Node UA or none).
- **Fix:** record the device label at `POST /auth/login` / `mfa/verify` / passkey verify, where the forwarded browser UA is present, keyed by the new token's `jti`. Or have server-side fetches forward the browser's UA.

### AUX12-F04 · Passkeys are "unavailable" on any stack without a public https URL, and the admin is not told · minor

- **Repro:**
  1. Gracious stack, `public_url` empty.
  2. Any local user opens `/profile#security`.
- **Observed:**
  - The Geçiş anahtarları row says "Geçiş anahtarları için panelin genel adresi (https) ayarlanmalı. Yöneticinize başvurun.";
  - `GET /org/public` answers `passkeys.enabled:false`;
  - but the policy tab shows the "Geçiş anahtarları" switch on, with no hint that it has no effect.
  - `_rp_ok()` ignores the request origin (`backend/app/services/mfa.py:579`, used at :611, :1239, :1432), although `passkeys.relying_party()` accepts a localhost origin outside prod.
  - Side effect: `au-signin-security.spec.ts` §16.4 cannot pass on such a stack, and on `127.0.0.1` no stack can, because WebAuthn rejects an IP as RP ID.
- **Expected:** the admin sees why the switch does nothing.
- **Fix:**
  - under the passkeys switch in `components/settings/signin-security.tsx`, show "Panelin genel adresi ayarlanmadan geçiş anahtarları çalışmaz" with a link to Entegrasyonlar;
  - let `_rp_ok` accept the dev origin rule;
  - document `http://localhost:<port>` for e2e.
